# Review, v2.1, 2026-11-24

**Reviewed by**: Independent Review Subagent (author on Gemini / Antigravity)
**Scope**: 5 key files reviewed directly (plus supporting pipeline, repository, frontend, and test files; full `git diff` blocked by sandbox error `readwrite D:\WORK\resume_ranker\backend\src\config\aws.py: non-absolute file path`), branch vs base
**Verdict**: Blocked

## Summary
Branch `v2.1` successfully removes authentication barriers in line with HC-01 and ADR-07, removes the S3 `results.json` read-modify-write race by storing recruiter decisions in DynamoDB, and introduces an atomic `transact_write_items` outbox commit for document upload completion. However, three production blockers remain: partial candidate decision updates overwrite existing decisions, statuses, and tags; concurrent upload completions collide on optimistic locks after committing the outbox transaction (returning HTTP 500 and corrupting counters); and job/resume deletion misses session-scoped S3 PDF keys, leaking candidate PII in S3. Note that `run_command` was blocked by a host sandbox configuration error, so this review is based on direct static inspection of the codebase and tests rather than live command execution.

## Blockers
### 🔴 Partial candidate decision updates wipe existing decision, status, and tags, `backend/src/api/routes/jobs_v2.py:339`
**Problem**: In `DecisionUpdateRequest` (`backend/src/api/routes/jobs_v2.py:339`), `tags` defaults to `Field(default_factory=list)` (`[]`) instead of `None`. Additionally, at `backend/src/api/routes/jobs_v2.py:1822` and `:1840`, `raw_decision = (body.decision or "").strip().lower()` turns an omitted `decision` (`None`) into `""`, and `if raw_decision is not None:` evaluates to `True`, adding `"decision": ""`, `"human_decision": ""`, `"status": None`, and `"tags": []` to `decision_payload` on partial PATCH requests.
**Why it matters**: Whenever a recruiter adds or edits a note via `CandidateActions.tsx:93` (`{"note": "..."}`), `save_candidate_decision` overwrites their existing `shortlisted` / `rejected` / `interview` decision, `status`, and `tags` in DynamoDB with empty values, permanently losing recruiter decisions on reload. The unit test at `backend/tests/unit/test_standalone_architecture.py:303-305` asserted `is not None` rather than key absence, so it passed despite the overwrite.
**Suggested fix**: Change `DecisionUpdateRequest.tags` to `Optional[List[str]] = None`. Only set `decision`, `human_decision`, and `status` in `decision_payload` when `body.decision is not None` (and reject blank strings if `body.decision == ""`). Return the merged item attributes from `save_candidate_decision` in the response, and update the test to assert `"decision" not in payload`, `"human_decision" not in payload`, `"status" not in payload`, `"decision_reason" not in payload`, and `"tags" not in payload`.

### 🔴 Concurrent upload completions race on version locks and corrupt counters, `backend/src/api/routes/jobs_v2.py:1051`
**Problem**: `frontend/src/lib/api.ts:395` executes up to 4 concurrent `completeDocumentUpload` requests against `complete_document_upload` (`backend/src/api/routes/jobs_v2.py:993`). After `commit_file_upload_with_outbox` commits `DOC#` as `UPLOADED` and dispatches `FAST_PARSE`, lines 1072-1078 call `_sessions_repo.increment_uploaded_count` and `_jobs_repo.increment_document_count` with `ConditionExpression="#v = :expected_version"` and zero retry handling (using `fresh_job` read before the transaction at line 1051). Moreover, `create_upload_session` (`backend/src/api/routes/jobs_v2.py:963`) already incremented `job.document_count` by `len(file_items)`, so line 1078 double-counts `document_count`.
**Why it matters**: Under normal frontend concurrency of 4, concurrent `/complete` requests collide on `SESSION#` and `JOB#METADATA` versions and throw unhandled `ConditionalCheckFailedException` HTTP 500s. Because `commit_file_upload_with_outbox` already marked `DOC#` as `UPLOADED` and sent the SQS message, retries hit the idempotency return at line 1016 without incrementing `uploaded_document_count`, permanently corrupting session counts, while `uploadResumesViaSession` treats the 500 as a failed upload and drops valid resumes from `fileIdMap`.
**Suggested fix**: Remove the duplicate `_jobs_repo.increment_document_count` call from `complete_document_upload`. Guard the `DOC#` transition inside `commit_file_upload_with_outbox` with a `ConditionExpression` (see Major below) and either increment `uploaded_document_count` atomically using `ADD uploaded_document_count :one` (or retry `increment_uploaded_count` on `ConditionalCheckFailedException`) only when the document actually transitioned from `UPLOAD_INITIALIZED` / `PENDING` to `UPLOADED`.

### 🔴 Job and resume deletion leak upload session S3 PDFs, `backend/src/api/routes/jobs_v2.py:1749`
**Problem**: `create_upload_session` (`backend/src/api/routes/jobs_v2.py:918`) writes resume PDFs under `{job_org_id}/jobs/{job_id}/sessions/{session_id}/resumes/{doc_id}.pdf` (where `job_org_id` defaults to `job_{job_id}`). However, `delete_job` (`backend/src/api/routes/jobs_v2.py:1749`) only purges S3 prefix `jobs/{job_id}/` (and without `list_objects_v2` pagination), and `delete_resume` (`backend/src/api/routes/jobs_v2.py:1800`) hardcodes `Key=f"jobs/{job_id}/raw/{document_id}.pdf"` instead of reading `file_item.s3_raw_key` or `doc_item.s3_pdf_key`. `delete_job` also leaves `PK=OUTBOX#{job_id}` and `PK=ORG#{job_org_id}/ACTIVE_SESSION#` items behind.
**Why it matters**: Deleting a job or resume uploaded via the primary upload-session flow returns HTTP 200 `"deleted"` while silently leaving candidate PII PDFs orphaned indefinitely in S3, and leaving active session pointers intact until the 30 minute expiry.
**Suggested fix**: In `delete_job`, paginate and purge both `f"jobs/{job_id}/"` and `f"{job_org_id}/jobs/{job_id}/"` (plus any explicit `s3_pdf_key` / `s3_raw_key` prefixes from DynamoDB items before deleting DynamoDB records), and clean up `OUTBOX#{job_id}` and `ORG#{job_org_id}` `ACTIVE_SESSION#` records. In `delete_resume`, load the `FileItem` and `DocumentItem` first and delete their actual recorded S3 keys.

## Major
### 🟠 Outbox transaction lacks ConditionExpressions on FILE and DOC items, `backend/src/infrastructure/queue/outbox.py:149`
**Problem**: `commit_file_upload_with_outbox` (`backend/src/infrastructure/queue/outbox.py:149-208`) updates `FILE#{file_id}` and `DOC#{file_id}` inside `transact_write_items` without any `ConditionExpression`.
**Why it matters**: Two concurrent `/complete` requests for the same `document_id` can both pass the route's pre-check at `jobs_v2.py:1016`, both succeed in `transact_write_items`, and both enqueue duplicate `FAST_PARSE` jobs. Worse, if a background worker has already advanced `DOC#` to `FAST_PARSING` or `STRUCTURED_PARSED`, an in-flight `/complete` call unconditionally resets its status back to `UPLOADED`, and a missing `FILE#` record causes DynamoDB `Update` to materialize an incomplete stub item missing `job_id`, `file_id`, `filename`, and `s3_raw_key`.
**Suggested fix**: Add `ConditionExpression` requiring `attribute_exists(PK) AND #st IN (:init, :pending)` on `DOC#{file_id}` (and `attribute_exists(PK)` on `FILE#{file_id}`), and handle `TransactionCanceledException` cleanly in `complete_document_upload` by re-reading `doc` and returning idempotent 202 when already `UPLOADED` or past it.

### 🟠 Unpaginated DynamoDB scan in outbox relay drops pending records, `backend/src/infrastructure/queue/outbox.py:279`
**Problem**: `relay_pending_outbox` (`backend/src/infrastructure/queue/outbox.py:279-288`) executes `dynamodb.scan(..., FilterExpression="entity_type = :et AND #st = :pending", Limit=max_records)` without checking `LastEvaluatedKey` (the same pattern exists in `backend/src/infrastructure/repositories/files_repository.py:879-917`), and never increments `attempts` or dead-letters failing items. Furthermore, `outbox.py` (`PK=OUTBOX#{job_id}`) and `files_repository.py` (`PK=JOB#{job_id}, SK=OUTBOX#...`) maintain two separate outbox schemas that do not reconcile each other.
**Why it matters**: In DynamoDB, `Limit` caps the number of raw table items evaluated *before* `FilterExpression` is applied. Once the single table contains more than 50 items (a single job with 25 resumes creates 51+ items), `relay_pending_outbox` scans only the first 50 items and misses pending outbox records permanently until their 24h TTL expires.
**Suggested fix**: Replace the full-table scan with a sparse GSI on pending outbox records (per HC-06 / ADR-04) or paginate `scan` across `LastEvaluatedKey` until `max_records` matching items are collected, track `attempts` with backoff/DLQ exhaustion, and unify the two outbox formats.

### 🟠 Upload session existence is not validated before outbox commit, `backend/src/api/routes/jobs_v2.py:1006`
**Problem**: In `complete_document_upload` (`backend/src/api/routes/jobs_v2.py:1006-1013`), session validation checks `if session_id and doc.session_id and session_id != doc.session_id: raise HTTPException(400, ...)`. It never verifies that `_sessions_repo.get(job_id, session_id)` exists, and skips the check altogether if `doc.session_id` is `None`.
**Why it matters**: If a `DocumentItem` has `session_id=None`, passing an arbitrary or foreign `session_id` in `/upload-sessions/{session_id}/documents/{document_id}/complete` passes validation and writes that unverified `session_id` into the outbox event.
**Suggested fix**: When `session_id` is supplied in the route, require `_sessions_repo.get(job_id, session_id)` to exist under `job_id` (returning 404 if absent) and reject if `doc.session_id != session_id` (even when `doc.session_id` is `None`).

### 🟠 Unsanitized client `filename` and `org_id` interpolated into S3 keys, `backend/src/api/routes/jobs_v2.py:481`
**Problem**: `check_ats_endpoint` (`backend/src/api/routes/jobs_v2.py:481`) constructs `s3_key = f"ats_check/{uuid.uuid4().hex[:8]}_{file.filename}"` using the raw client `file.filename`, and `CreateJobRequest.org_id` (`backend/src/api/routes/jobs_v2.py:182, 375`) accepts arbitrary unvalidated strings interpolated into `s3_key = f"{job_org_id}/jobs/{job_id}/..."` at line 918.
**Why it matters**: Crafted `filename` or `org_id` values containing `/` or `..` segments allow S3 key/prefix traversal, risking accidental or malicious reads/overwrites of keys in other prefixes (such as `jobs/`), violating `AGENT.md` upload rules ("use generated filenames... cover path traversal").
**Suggested fix**: Use a purely server-generated key for `/ats-check` (for example `f"ats_check/{uuid.uuid4()}.pdf"`), and validate `CreateJobRequest.org_id` against a strict slug regex (`^[a-zA-Z0-9_-]{1,64}$`) or reject client-supplied `org_id` outside test overrides.

### 🟠 Direct `fitz` import in API route violates HC-03 and blocks event loop, `backend/src/api/routes/jobs_v2.py:522`
**Problem**: `parse_jd_endpoint` (`backend/src/api/routes/jobs_v2.py:509-531`) imports `fitz` directly inside `api/routes/jobs_v2.py` and runs synchronous `fitz.open(stream=contents, filetype="pdf")` directly inside an `async def` route handler.
**Why it matters**: `projectrequirement.md` Hard Constraint HC-03 explicitly forbids `fitz` outside the Parsing Module ("ALLOWED ONLY in the Parsing Module. Forbidden in API/Scoring"). Running PyMuPDF synchronously inside an async handler also blocks the FastAPI event loop and violates PyMuPDF's thread-safety constraints if concurrent requests arrive.
**Suggested fix**: Move JD PDF text extraction into the parsing module (e.g. a dedicated function/service in `src/extraction/` using isolated execution or `asyncio.to_thread`) and call that service from `parse_jd_endpoint`.

### 🟠 Synchronous `boto3` and scoring calls block FastAPI `async def` routes, `backend/src/api/routes/jobs_v2.py:345`
**Problem**: Nearly all route handlers in `backend/src/api/routes/jobs_v2.py` (`create_job`, `create_upload_session`, `complete_document_upload`, `analyze_job`, `get_job_status`, `extract_resumes_stream`, `score_job_endpoint`, `get_results`, `download_resume`, `delete_job`, `update_candidate_decision`, `export_job_csv`) are declared `async def` while calling synchronous blocking `boto3` I/O directly on the asyncio event loop (`extract_resumes_stream` polls DynamoDB synchronously every 0.5s; `score_job_endpoint` runs full candidate scoring synchronously).
**Why it matters**: Under concurrent uploads (`concurrency=4`), active SSE streams, or large candidate cohorts, blocking the single asyncio event loop stalls health checks, parallel `/complete` calls, and other API requests.
**Suggested fix**: Either convert non-streaming I/O-bound routes to `def` (so FastAPI dispatches them to its anyio threadpool automatically) or offload blocking repository, storage, and scoring calls via `await asyncio.to_thread(...)`, especially inside `extract_resumes_stream` and `score_job_endpoint`.

### 🟠 Missing `import time` breaks job status retry in `final_rank_worker.py`, `backend/src/pipeline/final_rank_worker.py:262`
**Problem**: `final_rank_worker.py:262` calls `time.sleep(0.05)` inside the `jobs_repo.update_status` optimistic lock retry loop, but `time` is never imported in `backend/src/pipeline/final_rank_worker.py:1-36`.
**Why it matters**: If `jobs_repo.update_status` encounters any `ConditionalCheckFailedException` (e.g. concurrent job update), `time.sleep(0.05)` raises `NameError`, jumping to the outer `except Exception` at line 269 and marking a successfully scored upload session as `FAILED`.
**Suggested fix**: Import `time` at the top of `backend/src/pipeline/final_rank_worker.py`.

### 🟠 Standalone architecture test suite has tautological and bug-masking tests, `backend/tests/unit/test_standalone_architecture.py:200`

## Minor
### 🟡 Incomplete uploads deadlock upload session finalization, `backend/src/api/routes/jobs_v2.py:1093`
**Problem**: If 1 of N files in an upload session fails its client S3 PUT (so its `DocumentItem` stays `UPLOAD_INITIALIZED`), `finalize_upload_session` (`backend/src/api/routes/jobs_v2.py:1093-1128`) does not mark un-uploaded documents `FAILED` or `REMOVED`. Furthermore, `analyze_job` (`jobs_v2.py:1274-1298`) enqueues `FAST_PARSE` for `PENDING_UPLOAD` files if `req.file_ids` is omitted, and `request_analysis` only marks `FileItem`s `REMOVED`, leaving `DocumentItem`s in `UPLOAD_INITIALIZED`.
**Why it matters**: `coordinator.py:87` requires `all(d.status.is_terminal_fast_parse() for d in documents)`, so a single failed browser upload permanently stalls the upload session in `FAST_PREPROCESSING`.
**Suggested fix**: Reconcile uncompleted `UPLOAD_INITIALIZED` documents in `finalize_upload_session` (matching `architecture.md` Lifecycle 2), skip `PENDING_UPLOAD` files during `analyze_job`, and sync `DocumentItem` status when `FileItem`s are marked `REMOVED`.

### 🟡 `delete_resume` DocumentItem sync always raises TypeError, `backend/src/api/routes/jobs_v2.py:1795`
**Problem**: `delete_resume` calls `_docs_repo.update_status(job_id, document_id, DocumentStatus.FAILED, error_message="User deleted resume")`, whereas `DocumentsRepository.update_status` (`backend/src/infrastructure/repositories/documents_repository.py:66-73`) requires `expected_version: int` and has no `error_message` parameter. The `TypeError` is silently swallowed at line 1796.
**Why it matters**: Deleted resumes remain in non-terminal state in `DOC#` items, corrupting `get_extraction_metrics` and `coordinator.py` barrier checks.
**Suggested fix**: Use `_docs_repo.update_status_conditional` with `extra_updates={"error_reason": "User deleted resume"}` when the `DocumentItem` exists.

### 🟡 `scoring_repository.py` alias collision, float serialization, and timestamp precision bugs, `backend/src/infrastructure/repositories/scoring_repository.py:190`
**Problem**: `save_candidate_decision` builds `val_alias = f":{k}"` (`:192`), which can collide with fixed aliases (`:now`, `:zero`, `:one`, `:et`, `:jid`, `:did`, `:expected_v`, `:client_ts`) or break DynamoDB expressions on keys with hyphens/dots, and does not apply `to_decimal(v)` to floats. Additionally, `updated_at` uses 1-second `%Y-%m-%dT%H:%M:%SZ` formatting while `client_timestamp` (`:206`) uses lexicographical `updated_at <= :client_ts`: fractional ISO timestamps like `...19.500Z` sort before `...19Z` (`'.' < 'Z'`), falsely failing same-second writes, and `ConditionalCheckFailedException` is not caught in `jobs_v2.py:1851` to return HTTP 409.
**Why it matters**: Arbitrary keys or float values can trigger DynamoDB `ValidationException`/`TypeError`, same-second fractional client timestamps can be rejected, and version conflicts surface as 500 instead of 409.
**Suggested fix**: Use indexed value placeholders (`:val_{i}`), pass values through `to_decimal`, parse/normalize timestamps or use millisecond ISO format consistently, and translate `ConditionalCheckFailedException` to HTTP 409 in `update_candidate_decision`.

### 🟡 `scoring_worker.py` writes wrong field names on `ScoringItem`, `backend/src/pipeline/scoring_worker.py:204`
**Problem**: `scoring_worker.py:204-211` passes `weights=job.weights` and `s3_results_key=f"jobs/{job_id}/results.json"` to `ScoringItem`, whereas `ScoringItem` (`backend/src/infrastructure/models/scoring.py:42,48`) defines `s3_result_key` (singular) and `weights_used`. Because Pydantic ignores extra kwargs by default, `s3_result_key` is persisted as `""`.
**Why it matters**: `get_results` (`jobs_v2.py:1606`) cannot fall back to `scoring_repo.get_latest(job_id)` when `ScoringItem.s3_result_key` is empty.
**Suggested fix**: Pass `s3_result_key` and `weights_used` to `ScoringItem` in `scoring_worker.py`.

### 🟡 Silently swallowed decision errors in `get_results` and missing fallback in `export_job_csv`, `backend/src/api/routes/jobs_v2.py:1629`
**Problem**: `get_results` (`backend/src/api/routes/jobs_v2.py:1629-1648`) catches all exceptions from `_scoring_repo.get_candidate_decisions(job_id)` and logs only at `debug`, returning candidates without human decisions. Meanwhile `export_job_csv` (`:1883-1888`) only reads `jobs/{job_id}/results.json` without falling back to `scoring_repo.get_latest(job_id)` and silently exports zero candidate rows on error.
**Why it matters**: Transient DynamoDB errors hide human shortlist/rejection decisions from recruiters without warning, and jobs stored under `scoring/{scoring_id}.json` export empty CSVs.
**Suggested fix**: Propagate or loudly warn/surface failure when authoritative decision lookup fails in `get_results`, and share the S3 result-loading helper (with `scoring_repo.get_latest` fallback and 409/500 handling) between `get_results` and `export_job_csv`.

### 🟡 Internal exceptions exposed and magic bytes skipped on `/ats-check` and `/parse-jd`, `backend/src/api/routes/jobs_v2.py:496`
**Problem**: `jobs_v2.py:496`, `:530`, and `:1676` interpolate raw exception strings (`{str(e)}`) into HTTP 500 `detail` payloads. Additionally, `/ats-check` (`:469`) and `/parse-jd` (`:514`) only check `.pdf` filename extension without verifying `%PDF-` magic bytes.
**Why it matters**: Violates `AGENT.md` guidelines ("Never expose stack traces/internal errors to users" and "Verify content type, not the extension").
**Suggested fix**: Return generic error messages to clients (keeping detailed exceptions in server logs only) and verify `contents.startswith(b"%PDF-")` on both endpoints.

### 🟡 SSE error handling, duplicate fallback polling, and missing timeouts in frontend API, `frontend/src/lib/api.ts:675`
**Problem**: In `subscribeToJobExtraction` (`frontend/src/lib/api.ts:675-677`), the `'error'` listener treats backend `event: error` frames identically to transient network errors without reading `e.data` or closing `es`, while `AnalyzeButton.tsx:267-278` starts `/status` polling unconditionally after 2s even when SSE is healthy. Also, `checkAts` (`api.ts:833`) and `exportCandidatesCsv` (`api.ts:869`) have no `AbortController` timeout, and `checkAts:847` / `uploadResumesToBackend:557` assign `data.detail` directly even when FastAPI returns an object or validation error array (`[object Object]`).
**Why it matters**: Server-emitted job failures do not cleanly terminate SSE or display the server error message, double polling multiplies DynamoDB reads, and hung ATS checks hang the UI indefinitely.
**Suggested fix**: Distinguish `MessageEvent` (`'data' in e`) from network `Event` in `subscribeToJobExtraction` (closing `es` on server terminal error events), delay/gate fallback polling in `AnalyzeButton` on actual SSE failure or inactivity, add `AbortController` timeouts to `checkAts` and `exportCandidatesCsv`, and extract `.message` / stringify structured FastAPI `detail` payloads safely.

### 🟡 Unbounded in-memory rate-limit dict and insecure CSRF/cookie defaults, `backend/src/api/routes/jobs_v2.py:104`
**Problem**: `_session_job_timestamps` (`jobs_v2.py:104-123`) never evicts inactive `session_id` keys, leaking memory across unique requests; `get_session_id` (`:139`) hardcodes `secure=False`; and `enforce_session_ownership` (`:145-160`) reads `os.environ.get("ENVIRONMENT")` directly (ignoring `.env` settings), takes an unused `job` parameter, and skips the origin check when `FRONTEND_URL` is empty.
**Why it matters**: Long-running servers accumulate unbounded keys, session cookies lack `Secure` in HTTPS production, and misconfigured `FRONTEND_URL` silently disables production CSRF protection.
**Suggested fix**: Evict empty/expired session entries in `_session_job_timestamps` (or bound cache size), set `secure=is_prod`, read environment via `get_settings()`, fail closed in prod if `FRONTEND_URL` is unconfigured, and rename `enforce_session_ownership` to reflect its CSRF origin-check responsibility.

## Strengths
- Cleanly implements HC-01 and ADR-07 across all `/api/v2/jobs` routes and `frontend/src/lib/api.ts` with zero auth dependencies and open endpoint contracts.
- Eliminating S3 `results.json` read-modify-write mutations from `update_candidate_decision` in favor of DynamoDB `DECISION#` overlay at read time (`get_results` and `export_job_csv`) removes a major lost-update concurrency hazard.
- Moving `commit_file_upload_with_outbox` into a single `transact_write_items` call with fail-closed HTTP 500 handling in `complete_document_upload` (and preserving `FileItem`, `DocumentItem`, and `OutboxItem` atomicity) is the right architectural pattern once the missing `ConditionExpression` and counter concurrency races are resolved.
- Job creation defaults to the complete server-generated UUID namespace (`job_{job_id}`) rather than a truncated 8-character prefix, avoiding hash/prefix collisions.
